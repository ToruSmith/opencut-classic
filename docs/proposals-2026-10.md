# 功能提議(2026-10-27,給工程師評估)

這是 Toru 看過、同意「可以評估」的 6 項提議,**不是指令**。你(工程師)先評估,再決定做不做、做哪些、怎麼做。求穩:任何一項評估後覺得風險太高,可以寫「不做」或「改做較小的版本」,不必硬做完。

## 怎麼使用這份文件

1. **先評估。** 讀完全文與 `AGENTS.md`,在文末「評估紀錄」表填:每項「做 / 改做 / 不做」、一行理由、你估的規模(S / M / L)。評估結果隨第一項的 push 一起送出即可,不必單獨 push。
2. **照建議順序,每次最多做兩項。** 一項做完就 push 一次(一項一個 commit,不要混在一起),CI 全綠、文件更新後才算完成。第二項若風險比預期高,可以停在第一項。任何時候都可以停下,Toru 不要求全部完成。
3. 不要為這些事停下來問:命名、檔案位置、繁中文案、測試怎麼寫、沿用現有元件。自己決定,寫進該項的完成紀錄。
4. **只有這幾種情況才停下來問**(一次問完,附你建議的預設):
   - 會刪除或改變使用者既有資料 / 儲存格式(要寫遷移)。
   - 要新增依賴套件,或需要金鑰、外部服務。
   - 這份文件與 `AGENTS.md` 或程式碼互相矛盾,且看程式碼也判斷不出誰對。
   - 要動 `main` 分支或專案設定。
   - 同一個 CI 錯誤修了 3 次仍失敗。
5. 這份文件裡標「(先確認)」的地方,是提議者只看了目錄、**沒有讀過程式碼**的推測。請你以程式碼為準,推測錯了就直接改寫評估。
6. 做完一項:更新 `AGENTS.md` 的功能地圖、`docs/qa-checklist.md`(實機驗收步驟)、`README.md` 的「近期新增」(給使用者看的說法)。不要宣稱「畫面正常」,這個環境看不到畫面。

## 共通:效能與卡頓守則(每一項都適用)

這個編輯器的預覽是即時的,卡頓比功能缺少更讓人受不了。每項提議動工前後都照這些做:

- **先量再改。** 用 `window.__renderPerf = true`(見 `AGENTS.md`)記下改動前後的各階段耗時,把數字寫進完成紀錄。預覽品質(`quality: "preview"`)下,新功能不應讓 1080p 專案的播放明顯變差。你看不到畫面、也跑不了 GPU,所以**做不到實測的部分,明確寫「未實測,請 Toru 實機確認」**。
- **不要每格配置新物件。** 貼圖用合成器的貼圖池(`acquire`),不要每個 pass 新建貼圖;上傳影格沿用 `staging` 中轉畫布。
- **一個 shader 一個 pass 為原則。** 新增的全畫面 pass 會乘上「同時可見的片段數」。先確認沒有在時間範圍外的片段也被繪製(先確認:渲染樹是否只含當前時間可見的元素)。
- **大量片段是第二個風險。** 一次產生幾十到幾百個片段(自動排片、逐字字幕)會拖慢時間軸 UI 與渲染樹重建(`sceneRebuild`)。能用「一個片段 + 關鍵影格」就不要拆成多個。必須拆時,設上限並在介面提示。
- **切很多小段 = 每個切點都要重新定位解碼。** 沿用現有建議:先對素材「建立代理檔」。凡是會產生大量小段的功能,在介面上偵測沒代理檔時提示使用者。
- **單一復原步驟。** 批次操作一律合成一步(`BatchCommand` 或 `QuickCutCommand` 的做法),不要讓復原堆疊暴增。
- **耗時分析一律串流分段、動態載入。** 沿用 `createTimelineAudioStream` 與 `await import("mediabunny")`;不要把整首歌解成一個大緩衝,不要在會被專案列表引用的檔案靜態 import 重量級套件。
- **邏輯寫成純函式並附測試。** 這環境沒有 GPU 和 node_modules,純函式測試才是你唯一能自己跑的驗證(`bun test`)。
- **shader 只能靠 CI 的 `shaders` job 驗證。** 壞一個,所有效果一起壞。改 `.wgsl` 要特別小心,uniform 固定 8 個浮點數。

## 前置檢查(提議之外,但建議先做)

這兩件會影響後面所有節拍相關功能,而且都便宜:

- **節拍偵測的真實音樂準確度。** `AGENTS.md` 自己寫了「只用合成節拍測過」。你沒有音訊可聽,請在完成紀錄寫「需 Toru 用 3~5 首不同類型的歌實測」,並列在 `qa-checklist.md`。
- **節拍書籤可手動微調**(拖動或補一個節拍點)。全自動偏了現在只能整批重跑。這是補強準確度成本最低的方法,評估看看。

## 提議 1:LRC 歌詞匯入 + 點拍同步字幕

**建議順序:1(先做)。規模:S(LRC)+ M(點拍)。風險:低。**

### 目標
- 匯入 `.lrc` 檔,變成字幕片段(與現有 SRT / ASS 匯入同一條路)。
- 沒有時間軸的純歌詞,可以在播放音樂時按鍵逐句打時間(點拍同步)。

### 為什麼
字幕目錄現有 `srt.ts`、`ass.ts`、`parse.ts`、`insert.ts`(先確認:沒有 LRC)。LRC 是歌詞最普遍的格式,配合節拍剪輯就是歌詞影片的基本入口。

### 借鏡
JIZURA(MIT、同作者):LRC 記法與點拍同步的操作流程。**只借規格與流程**;JIZURA 是 Canvas 2D,這裡是純邏輯與 UI 流程,所以可以直接借,不涉及繪製。

### 做法建議
- 新增 `subtitles/lrc.ts`:`parseLrc({ input })`,回傳與 `parse.ts` 其他格式相同的結果(`captions`、`skippedCueCount`、`warnings`),在 `parse.ts` 加 `case "lrc"`。純函式,附測試。
- 規則(這些是建議的預設,你可調整並記錄):
  - 行格式 `[mm:ss.xx]歌詞`;`xx` 可為 2 或 3 位;一行可有多個時間戳(同一句歌詞出現多次)。
  - 每句結束 = 下一句開頭;最後一句給固定長度(建議 4 秒);單句最長設上限(建議 10 秒),避免前奏、間奏的長空白被拉成一句。
  - `[offset:±ms]`:`起點 = 時間戳 - offset / 1000`。
  - 只有時間戳沒有文字的行 = 結束上一句(常用來標示間奏)。
  - 逐字時間戳(Enhanced LRC 的 `<mm:ss.xx>`)第一版先去掉,只保留整句。
  - 結果按起點排序。
- 點拍同步(M):
  - 流程:貼上純歌詞 → 播放音樂 → 每句開始按一次鍵(建議 Space,或下一句鍵)→ 記錄時間 → 完成後產生字幕片段。支援「回退一句重打」。
  - **時間一律取自播放頭(音訊時鐘),不要用 `Date.now()` 或 `setTimeout` 估計**,否則會因為渲染卡頓而偏。
  - 按鍵記錄只寫進本機暫存陣列,**不要每按一下就更新 zustand 全域狀態並重繪整個編輯器**;完成時一次寫入。

### 效能與卡頓注意
- LRC 解析本身便宜。風險在「一次插入大量字幕片段」(一首歌 40~80 句)。用現有 `insertElements` / `BatchCommand` 一次放入,單一復原步驟。
- 點拍期間音樂正在播放,按鍵處理要輕:不要在按鍵 handler 裡做排版量測或寫儲存。

### 驗收
- 測試:正常、多時間戳、offset、空文字行、亂序、壞行(略過並回報 `warnings`)。
- 實機:匯入一首歌的 LRC,字幕時間與歌曲對得上;點拍流程能回退重打;`Ctrl+Z` 一次全部復原。

## 提議 2:進度式擦除轉場(擦除、光圈、時鐘)

**建議順序:2。規模:M。風險:中(要靠實機看畫面)。**

### 目標
補上現在沒有的「真正的擦除」:線性擦除、圓形光圈、時鐘掃過,都能做出柔邊。

### 為什麼
`AGENTS.md` 已記:遮罩參數不能做關鍵影格,所以現有的「滑動擦除」只是片段滑進來。我看到 `animation/effect-param-channel.ts` 存在(先確認:**特效參數**是否能做關鍵影格、有沒有緩動)。若可以,做成「帶進度參數的特效」,再用關鍵影格動畫那個進度,就能有真擦除,**不必動專案格式,也不必寫遷移**。這是 `AGENTS.md` 自己列的「風險小得多」的那條路。

### 借鏡
FreeCut(MIT)的轉場清單、gl-transitions。**注意授權:** gl-transitions 是逐檔授權,沒逐檔確認前只借「效果名稱與數學構想」,不要貼 GLSL。擦除、光圈、時鐘的數學都很簡單(距離、角度、smoothstep),自己用 WGSL 寫就好,不需要搬任何程式碼。

### 做法建議
- 一個 shader 一個 pass,把 `progress`、`softness`、模式相關參數塞進 8 個浮點數(`resolution`、`direction` vec2、`scalars` vec4)。可以考慮一支 shader 用模式參數切換,或各自一支;**以不增加每格開銷為準**。
- 效果作用在「畫面大小的圖層」(`AGENTS.md` 已記),所以擦除是相對整個畫面,不是片段邊界。轉場套用時是對上層片段加這個特效、把 `progress` 做 0 → 1 的關鍵影格。
- 套用走轉場面板「兩段之間」現有流程(`applyElementEdits`,單一復原步驟);配對邏輯沿用 `findTransitionPair`。
- 新增流程照 `AGENTS.md`「新增效果」四步,並加到 `shader_tests.rs` 的 `SHADERS`。

### 效能與卡頓注意
- 這是**全畫面的額外 pass**,轉場期間才有,風險可控;但請確認轉場前後該特效不會繼續留在片段上空轉(最好特效片段只覆蓋轉場那一段)。
- 關鍵影格在預覽時每格要求值,確認 `effect-param-channel` 的求值沒有每格配置新物件。
- 沒有 GPU 可實測:**shader 通過 naga 不代表畫面對**。完成紀錄要明講「畫面未驗證」,並在 `qa-checklist.md` 寫清楚:每種擦除的起點、終點、柔邊、方向。

### 驗收
- 純函式(進度映射、參數換算)有測試;CI `shaders` 全綠。
- 實機:三種擦除在預覽與匯出一致;柔邊參數有效;進度 0 與 1 時畫面等於完全未擦 / 完全擦完(這是最容易目測的錯誤)。

## 提議 3:自動從素材庫排滿整首歌(簡化版)

**建議順序:3。規模:M~L。風險:中。這項最容易做過頭,請先做最小版本。**

### 目標
使用者選一批素材(影片或圖片)+ 已分析好節拍的音樂,一鍵依節拍把素材排滿整條時間軸。

### 為什麼
`AGENTS.md` 已列為頭號缺口(BeatEdit、mvmake、CapCut 自動剪輯的做法)。目前的一鍵快剪只處理「使用者已排好、同一條軌道」的素材。

### 做法建議
- **最小版本,不做智慧選片**:每個切點隨機(固定種子,可重現)從素材池抽一段,不重複連續抽同一支;抽不到時才允許重複。
- 邏輯寫成純函式 `planAutoCut({ beats, assets, seed, options })`,輸入節拍與素材長度,輸出「哪支素材、入點、出點、放在時間軸哪裡」的清單。**純函式能測**,這是你在沒有 GPU 時唯一能驗證的部分。
- 入點規則:避免太靠素材尾端(出點不得超過素材長度);素材比切段短時,從頭開始並允許變速的選項留到第二版。
- 影片素材預設**靜音**(音樂才是主聲軌);圖片素材給固定長度。
- 建立新片段要自己處理 trim 與連動音訊(`AGENTS.md` 警告過);不要碰 retime 與變速,第一版不做。
- 用 `QuickCutCommand` 的做法合成單一復原步驟。

### 效能與卡頓注意
- **這是最容易造成卡頓的一項**:一首 3 分鐘、每拍一刀的歌會產生 200 個以上的片段,每個切點預覽都要重新定位解碼。
  - 設切點數量上限,並沿用「最短片段」「每 N 拍」控制(`pickSplitTimes` 的 `minGap`)。
  - 偵測到素材沒有代理檔就在介面提示「建議先建立代理檔」。
  - 預設用每 2 或 4 拍,而不是每拍。
- 一次插入大量片段會觸發 `sceneRebuild`,請量一次(`__renderPerf`)。
- 時間軸 UI 在上百個片段下的表現(先確認:有沒有虛擬化、拖曳是否卡)。

### 驗收
- 測試:`planAutoCut` 的種子可重現、不超出素材長度、不連續重複、總長與音樂對齊。
- 實機:一首歌排出的結果可播放不卡頓;`Ctrl+Z` 一次全部復原;再按一次(換種子)能重排。

## 提議 4:逐字 / 逐句字幕動畫(卡拉 OK 填色、逐字出現)

**建議順序:4(等 2 做完再評估,因為可能直接重用它)。規模:M~L。風險:中高。**

### 目標
歌詞影片的招牌效果:一句歌詞隨演唱逐字填色,或逐字 / 逐詞出現。

### 為什麼
`text/` 目錄有排版與量測(先確認:沒有逐字動畫);現有的進出場動畫是整個片段套一組關鍵影格。

### 借鏡
JIZURA(逐字效果的種類與節奏)、FreeCut(逐字 / 逐詞 / 逐行文字動畫)。**兩者都是繪製邏輯,不能搬**,只借「想要的視覺結果」,用本專案的渲染樹重做。

### 做法建議(由簡到繁,評估時可只選第一種)
1. **逐句顯示**(最簡單):每句一個字幕片段,用現有進出場動畫。提議 1 做完就已經有了。
2. **卡拉 OK 填色(建議重點)**:每句用**兩個疊在一起的字幕片段**,上層用「高亮色」,並套用提議 2 的線性擦除特效,`progress` 依演唱時間做關鍵影格 0 → 1。**片段數是 2 倍的句數,不是字數。**
3. **逐字 / 逐詞出現**:要拆成多個文字元素,或讓渲染器支援逐字參數。**成本最高,而且中文沒有空格,逐字就是逐個字元,片段數暴增。** 除非有人真的想要,否則只在評估紀錄寫「不做 / 之後再說」。

### 效能與卡頓注意
- 逐字拆分會讓片段數 = 歌詞總字數(一首歌可能 500 字以上),幾乎一定會拖慢時間軸與渲染樹。**不建議第一版做。**
- 填色方案每個可見字幕多一個全畫面擦除 pass;同一時間只有 1~2 句可見,風險可控。請確認不在時間範圍內的字幕片段不參與繪製(先確認)。
- 字幕文字量測(`measure-element.ts`)在拆多個片段時會被重複呼叫,別在渲染路徑裡重算。

### 驗收
- 純函式(時間 → progress 關鍵影格)有測試。
- 實機:一首歌的歌詞填色與歌聲對得上;匯出與預覽一致;片段數沒有爆炸。

## 提議 5:匯出——只輸出選定範圍、綠幕 / 黑底合成用

**建議順序:5。規模:M(各一半)。風險:中,先做適配評估。**

### 目標
- 只匯出時間軸上選定的區間(入點到出點),檔名帶範圍。
- 匯出綠幕或黑底背景的版本,方便疊進別的剪輯軟體。

### 為什麼
先確認:`export/` 只有 `defaults.ts`、`index.ts`、`mime-types.ts`,實際匯出在 `services/renderer/scene-exporter.ts`;**範圍匯出是否已經有,需要你先查**。

### 借鏡
JIZURA 的「選んだ行だけ書き出す」與「合成用の背景」。**注意:** JIZURA 是在 Canvas 2D 繪製時把背景換純色、文字換白;本專案是 Rust 合成器,做法要重新評估:
- 範圍匯出:比較單純,範圍內的影格與音訊 chunk 才送進編碼器。
- 綠幕 / 黑底:先看合成器能不能在最後加一道「單色背景覆蓋」(背景層換成純色即可,可能**完全不需要 alpha 編碼**)。若要真 alpha 通道(透明 WebM / ProRes 4444),規模大很多,先不做。

### 效能與卡頓注意
- 匯出是整個流程最吃資源的路徑。**不要引入第二次全畫面讀回(readback)**,也不要為了換背景多繞一遍影格。
- 音訊匯出沿用分段串流(`createTimelineAudioStream`),範圍匯出只要起點與終點限定,**不要改成整段混完再裁**。
- 匯出進度要能取消(先確認是否已有)。

### 驗收
- 範圍起迄時間換算有純函式與測試(含與影格邊界對齊)。
- 實機:選一段匯出,長度與音畫同步正確;綠幕版在別的軟體可以摳色。

## 提議 6:音訊——自動壓低背景音(ducking)、EQ

**建議順序:6(最後,而且建議只做 ducking)。規模:M。風險:中。**

### 目標
- Ducking:有人聲 / 旁白時,自動把背景音樂壓低。
- EQ:簡單的低、中、高三段。

### 為什麼
有旁白或人聲加音樂的剪輯很常見,手動畫音量線很累。

### 借鏡
FreeCut(音訊 EQ)。

### 做法建議
- **最大的風險:預覽與匯出是兩套實作**(`AGENTS.md` 已記:預覽用 Web Audio 的 `DynamicsCompressorNode`,匯出用 `audio-mixer.ts` 的 `LookaheadLimiter`)。任何新的音訊處理**都要兩邊實作且結果一致**,否則會出現「預覽好聽、匯出不一樣」。
- **Ducking 先做**:對「主講軌」算一條低取樣率(例如 50 次 / 秒)的包絡線,轉成背景軌的增益曲線,乘進 `resolveEffectiveAudioGain`(跟音訊淡化一樣的路徑,所以預覽、匯出、轉錄、波形會自動套用)。包絡分析寫成純函式,串流分段、不要整首解碼。
- **EQ 第二階段**:預覽可用 `BiquadFilterNode`;匯出要在 `audio-mixer.ts` 用同樣的 biquad 係數公式自己算,並寫測試確認兩邊頻率響應一致。第一版若覺得風險太高,寫「不做」。

### 效能與卡頓注意
- 預覽時增益曲線排程用 Web Audio 的曲線 API,不要每個音訊 callback 重算。
- 匯出時 biquad 是逐取樣運算,5 秒一段的 chunk 在 TypeScript 裡通常夠快,但請量一下匯出總時間有沒有明顯變長。

### 驗收
- 純函式(包絡、增益曲線)有測試:靜音、突然出聲、持續說話。
- 實機:音樂在人聲出現時平順壓低、人聲結束後平順恢復(不要有爆音或抽動);預覽與匯出的聽感一致。
